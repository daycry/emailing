# Correcciones posteriores a QA2 — T09

QA2 permanece **13 aprobados / 7 fallidos**, sin reintentos ni casos omitidos. Este trabajo no reescribe su informe ni sustituye QA3 completa de veinte casos. Los originales de QA1/QA2 están archivados.

## Diagnóstico y corrección

- **Privacidad de CSV/EML:** el `ServeFile` instalado rechaza la URL sin firma antes de consultar su existencia: 403 fuera de producción y 404 en producción. Los perfiles reales de QA devuelven 403. E05/E07 exigen ahora ese estado exacto y ausencia del contenido privado; los 404 de recursos de otra cuenta permanecen estrictos. No se ha cambiado la autorización del producto.
- **Referencia de upload ajena:** un `updates.file` de tipo string sobre el snapshot donde `file=null` no proporciona el sintetizador `fil`. El antiguo 200 no acreditaba ejecución del control de vinculación. El caso obtiene una referencia firmada del upload auténtico del propietario, la entrega a `_finishUpload` en la sesión ajena y verifica `fil` en el snapshot firmado que generó Livewire. Después exige 403 al importar, igualdad de los recursos SQL de ambas cuentas y de los archivos temporales registrados, incluidos sus hashes. No fabrica snapshots ni desactiva firmas, y no atribuye el upload del propietario a la otra cuenta.
- **Creación de plantilla:** se retuvo la respuesta HTTP real de `create`, después de que el servidor la hubiera procesado. Los campos rellenados mientras estaba retenida eran válidos; al liberarla el nombre quedó vacío y el formulario dejó de ser válido, en ambos perfiles. El caso espera ahora `clickCall(create)` y nombre vacío antes de rellenar. Se conservan el formulario HTML válido, la denegación del servidor a cuerpos vacíos y la ausencia de persistencia.
- **Defecto de producto descubierto:** `ContactImports.render()` usaba `validate(listSearch)`, que limpia todo el error bag al validar correctamente. Los errores de `import` existían durante la acción pero desaparecían del HTML. Se cambió únicamente esa llamada por `validateOnly(listSearch)`, que mantiene los errores de los otros campos. Dos regresiones prueban errores visibles con archivo ausente/string inválido, persistencia del mensaje tras una búsqueda válida y ausencia de escrituras. El límite de 150 caracteres sigue validado mediante el `render` real y su `ValidationException`; esta comprobación no acredita la UX HTTP de una búsqueda de longitud excesiva.
- **Rechazo de SMTP externo:** el primer recorrido completo de E07 descubrió una expectativa posterior incorrecta: Livewire responde 200 con el mensaje visible `El valor seleccionado para mode no está permitido.`; no es una respuesta 422 de una API convencional. Se exige ahora 200 **junto con** el `role="alert"`, ese mensaje exacto y la igualdad completa de los recursos SQL anteriores/posteriores. `resources.php/status` añade solamente un SHA256 de las filas SQL crudas de `mail_settings`, ordenadas por ID y limitadas explícitamente a las cuentas A/B del fixture: así se detecta cualquier cambio de configuración, credenciales cifradas o timestamps sin publicar esos valores. La auditoría tampoco cambia y el modo sigue siendo log.
